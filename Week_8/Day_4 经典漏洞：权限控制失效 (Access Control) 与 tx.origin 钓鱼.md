# 经典漏洞：权限控制失效 (Access Control) 与 tx.origin 钓鱼

Parity 钱包被黑事件是智能合约安全领域教科书级别的案例，它完美展示了权限控制失效的灾难性后果。
今天我们就来讲讲权限控制和合约设计架构的漏洞。

## 1. tx.origin 钓鱼

我们先来第一步：`tx.origin` 钓鱼。

要理解钓鱼攻击，首先必须分清以太坊中两个极易混淆的身份 ID：

1.  **`msg.sender`**: 直接调用合约的那个地址。
2.  **`tx.origin`**: 交易的原始发起者。

我们来看一个链式调用的场景：

假设你（用户 A）通过一个去中心化交易所的路由合约 B，去购买代币 C。
调用链条是这样的：`用户 A -> 路由合约 B -> 代币合约 C`

现在请试着分析一下，站在最末端的**代币合约 C** 的视角，它看到的 `msg.sender` 和 `tx.origin` 分别是谁？

对于合约 C 来说：
*   **`msg.sender`**: 是直接敲门的人，即**路由合约 B**。
*   **`tx.origin`**: 是最初的交易发起人，也就是**用户 A**。

### 钓鱼场景复现

假设你有一个用来存钱的智能合约钱包，为了资金安全，开发者在转账函数中写了这样一行代码：

```solidity
// 只有钱包的主人（owner）发起的交易才能转账
require(tx.origin == owner);
```

黑客做了一个伪装成领取空投的**恶意合约**，你（UserA = owner）不小心调用了这个恶意合约。而这个恶意合约里面的内容是：一旦被调用，就立马去调用你的智能合约钱包把钱转走。

此时调用的链条变成了：`owner（你） -> 恶意合约 B -> 钱包合约 C`

当这个时候，`tx.origin` 是谁？
没错，**还是你**。

代码运行了 `require(tx.origin == owner);` 检查了一下，确实是你，那就放行。
结果黑客就把钱转走了。

虽然在这个情况是恶意合约在拿钱，但是钱包只检查了谁是源头，它误以为你本人在操作，于是把大门打开，资金瞬间清空。

### 如何防御

为了堵住这个漏洞，我们需要修改代码，确保**只有你自己**才能直接操作钱，而拒绝任何合约作为中间人。你需要把什么作为检查？

没错，就是 **`msg.sender`**。

我们只需要知道是谁在直接敲门即可。这就是为什么在鉴权的时候，现代合约总是使用 `msg.sender` 的原因。

## 2. Parity 钱包黑客事件与权限控制

接下来我们要看看实际案例，分析一下 Parity 钱包的代码逻辑。

Parity 钱包为了节省 Gas，采用了 **钱包合约（Wallet） + 库合约（Library）** 的架构。
钱包合约本身不写复杂的逻辑，而是通过 `delegatecall` 来调用库合约的代码执行。

Parity 钱包为了能够处理各种功能，写了一个逻辑：只要有人调用它，而且调用的函数它自己没有，它就会把这个请求通过 `delegatecall` 转发给库合约处理。

而在那个公共库合约中，有一个用来初始化的函数：

```solidity
// 库合约 (Library) 中的代码片段
function initWallet(address[] _owners, uint _required, uint _daylimit) {
    // 这行代码会设置钱包的拥有者列表
    // 注意：这里没有任何 require(msg.sender == owner) 之类的检查！
    initMultiowned(_owners, _required);
    
    // 设置每日转账限额
    initDaylimit(_daylimit);
}
```

开发者原本想的是，这个函数就在刚刚创建的时候用一下，之后就没人会用了。
黑客不这么想，他简单地给受害者钱包发送了请求，说：“初始化一下，把主人设置为我”。钱包就照做了，然后黑客就轻松把 3000 万美元的 ETH 转走了。

## 3. 现代化的防御手段：Initializer 模式

既然我们看到了漏洞，那我们应该学习如何防御。

在普通的 Solidity 合约中，我们通常使用 `constructor` 来进行初始化，它具备完美的特征：只在合约部署的一瞬间运行一次，然后永远消失。

但是在 Parity 这种 **钱包 + 库** 的组合中，我们不能直接用 `constructor` 来初始化钱包的数据。
因为在库合约中写了 `constructor` 来设置 owner，它只能作用于库合约，对于我们的钱包合约没有任何帮助。

这就有一个巨大的挑战：库合约构造函数对钱包合约毫无作用。于是开发者被迫放弃使用安全的 `constructor`，改用一个普通的函数来让钱包调用，以便通过 `delegatecall` 初始化钱包的数据。

这正是 Parity 漏洞的根源：**用普通函数替代了构造函数，但忘了给它穿上“防弹衣”。**

### Initializer 实现

为了解决这个问题，现代智能合约开发引入了一种标准化的防御机制，既能像构造函数一样运行一次，又能兼容代理模式。

我们通常会定义一个布尔变量或者一个版本号。

想一下，为了防止黑客像攻击 Parity 那样再次调用 `initWallet`，我们在 `initWallet` 函数应该先检查什么？初始化完成后要进行什么操作？

我们应该先检查是否是首次运行，然后在运行之后立马改为非首次。
这就是解决代理合约初始化问题的核心逻辑，我们通常称之为：**初始化模式**。

这就好比给房子配了一把只能用一次的钥匙，进门之后钥匙自己就断了，谁也进不来。

在代码实现上，通常被叫做 `initializer`，让我们来看看代码：

```solidity
// 定义一个开关，默认是 false (0)
bool private _initialized;

// 定义一个修饰符（Modifier），相当于给函数加的“安检门”
modifier initializer() {
    // 1. 检查：是不是第一次运行？(如果是 false 才能进)
    require(!_initialized, "Contract is already initialized");

    // 2. 锁定：设置为 true (1)，以后再也不能运行了
    _initialized = true;

    // 3. 执行：继续运行原本函数里的代码
    _; 
}

// 这里的 initWallet 加上了上面的“安检门”
function initWallet(address[] _owners) public initializer {
    // 真正的初始化逻辑...
    initMultiowned(_owners, ...);
}
```

### 防御效果

有了这层保护，我们再回到刚刚被黑的场景。

如果当时 Parity 加上了保护锁，当黑客试图调用 `initWallet` 的时候，合约会怎么样？
交易会 **Revert**（回滚）！

因为在正常的钱包创建流程中，`initWallet` 已经被调用过一次了，`_initialized` 变量已经被设为了 `true`。当黑客再次尝试调用时：

1.  `initializer` 修饰符运行。
2.  检查 `require(!_initialized)`。
3.  发现 `!true` 是 `false`。
4.  **Boom!** 交易失败，触发 Revert。

所有的状态修改（包括黑客想把 owner 改成自己的操作）都会被撤销，就像什么都没发生过一样。这就是现代代理合约最核心的防御机制。

## 总结

本章我们深入探讨了两个经典的权限控制相关漏洞：

1.  **tx.origin 钓鱼攻击**：
    *   **原理**：利用合约对交易发起者 (`tx.origin`) 的盲目信任。黑客可以通过中间恶意合约诱导用户发起交易，虽然 `msg.sender` 是恶意合约，但 `tx.origin` 仍然是用户。
    *   **防御**：在鉴权（Authorization）时，始终使用 `msg.sender` 而不是 `tx.origin`。`tx.origin` 仅在极少数特定场景（如限制非合约调用 `require(tx.origin == msg.sender)`）下使用。

2.  **Parity 钱包多签漏洞 (Access Control + Delegatecall)**：
    *   **原理**：为了节省 Gas 使用了代理模式，但初始化函数 (`initWallet`) 暴露为普通公共函数，且缺乏“仅能调用一次”的保护。黑客直接调用该函数接管了钱包的所有权。
    *   **防御**：使用 **Initializer** 模式。通过状态变量（如 `_initialized`）锁定初始化函数，确保其在合约生命周期内只能被执行一次。这是 OpenZeppelin `Initializable` 合约的核心逻辑，也是编写可升级合约（Upgradeable Contracts）的标准实践。

安全的核心在于：永远不要信任外部输入，永远不要预设函数的调用场景，明确每一个关键函数的权限边界。
