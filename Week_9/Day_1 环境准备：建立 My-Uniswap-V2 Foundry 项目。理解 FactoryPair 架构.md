# Day 1 环境准备：建立 My-Uniswap-V2 Foundry 项目，理解 Factory/Pair 架构

今天我们进入 My-Uniswap-V2 的开发。理解 Uniswap V2 的架构是编写和审计高级 DeFi 协议的基础。

今天的任务分为两部分：

1. 准备代码环境
2. 建立对核心架构的底层直觉

---

## 第一步：建立 Foundry 项目

打开终端，执行以下命令初始化一个干净的项目：

```bash
forge init My-Uniswap-V2
cd My-Uniswap-V2
```

进入项目后，删除默认生成的 `src/Counter.sol`、`test/Counter.t.sol` 和 `script/Counter.s.sol`。我们从零开始构建，保持工作区纯净。

---

## 第二步：理解 Factory / Pair 架构

Uniswap V2 的核心智能合约体系非常精简，采用了经典的**工厂模式**。整个系统被严格划分为两类合约：**全局的管理者**和**局部的执行者**。

### 1. Factory（工厂合约）— 管理全局

这是整个协议的**注册中心和模具**。

- **唯一性**：在整条链上，同一版本的 Uniswap 只有**一个**核心的 Factory 合约。
- **核心职责**：主要任务是**部署新的 Pair 交易对合约**。当用户想要为一组全新的代币（例如 tokenA 和 tokenB）建立交易市场的时候，他们必须通过 Factory 来触发创建。Factory 就会像流水线一样，部署出一个全新的 Pair 合约。

### 2. Pair（交易对合约 / 资金池）— 执行者

这是真正**沉淀资金和发生交易**的地方。

- **隔离与安全**：每一个交易对都有自己独立的 Pair 合约。这种设计保证了状态的独立性——一个资金池的计算逻辑或账本出现问题，绝不会波及到别的资金池。
- **核心职责**：保管池子里的两种代币储备，并处理所有核心业务逻辑，包括**兑换**、**添加流动性**和**移除流动性**。
- **双重身份**：Pair 合约不仅处理交易，它本身继承了 **ERC20 标准**。当流动性提供者将代币存入 Pair 的时候，该合约会直接向用户铸造并发送 **LP Token**。

> 通过这种架构，**Factory 负责"生"和"记账"**，而 **Pair 负责"管钱"和"交易"**，职责分明。

## 第三步：核心数据结构 — 嵌套 Mapping

为了让这套架构精确运转，Factory 需要在内部精确记录每一个被部署的 Pair 合约，以确保两种代币之间**永远只有一个资金池**，防止重复创建。

在 Solidity 的层面上，你会选择什么数据结构来存储呢？

答案就是：**`mapping`**。

不过又有一个新问题——我们常见的 mapping 是单键值对，比如 `mapping(address => uint256)` 来查一个用户的余额。但是我们现在不同，我们需要通过**两个独立的代币地址**，共同定位一个交易对合约的地址（也就是 Pair address）。

而且，Solidity 的语法不支持把两个变量并列作为键，比如 `mapping(address, address => address)` 是不合法的。我们需要用下面的**嵌套 mapping** 结构：

```solidity
mapping(address => mapping(address => address)) public getPair;
```

> 你用第一个钥匙（address）打开第一个抽屉，抽屉里还有各种小盒子，用第二个钥匙打开其中的一个小盒子，拿出来的 address 就是 Pair 的合约地址。

## 第四步：地址排序的必要性

但是，现在有个问题：

- 假如用户 A 输入的顺序是 `tokenA, tokenB`
- 用户 B 输入的顺序是 `tokenB, tokenA`

那么 `getPair[tokenA][tokenB]` 和 `getPair[tokenB][tokenA]` 指向的是**两个完全不同的存储槽**。如果不干预，就会出现两个不同的交易对，从而为相同的代币创建出两个独立的资金池——这样会导致**流动性分散**，影响交易效率和价格发现机制。

### 解决方案：规范化排序

为了解决这个问题，我们需要引入一个**"规范化"**的机制，确保对于任意两个代币，它们的 Pair 地址总是唯一的，无论用户以何种顺序输入代币地址。

在 Solidity 中，我们可以通过以下方式实现：

1. 定义一个内部函数，对输入的两个代币地址进行**排序**
2. 使用排序后的地址作为映射的键

其实就是直接比较地址的大小然后进行排序。在智能合约的底层，以太坊地址本质上就是一个 **160 位的十六进制整数**。Uniswap V2 的架构师采用了一个标准：**永远让地址小的那个作为 key1，地址大的那个作为 key2**。

```solidity
(address token0, address token1) = tokenA < tokenB ? (tokenA, tokenB) : (tokenB, tokenA);
```

通过这行代码，不管外部调用者先输入哪个地址，系统永远只会排成一种排列，然后去查找。这就彻底断绝了重复建池的漏洞。

## 总结

| 知识点 | 核心内容 |
|---|---|
| **Foundry 项目初始化** | 使用 `forge init` 创建项目，删除默认文件从零构建 |
| **Factory 合约** | 全局唯一的注册中心，负责部署和记录所有 Pair 合约 |
| **Pair 合约** | 每个交易对独立部署，负责资金保管与交易执行，同时也是 ERC20（LP Token） |
| **嵌套 Mapping** | `mapping(address => mapping(address => address))` 实现双键查找 |
| **地址排序** | 通过三元表达式确保 `token0 < token1`，防止重复建池 |

**今日核心收获**：Uniswap V2 采用 **Factory + Pair** 的工厂模式，Factory 负责创建和注册交易对，Pair 负责实际的资金管理和交易执行。为了保证每组代币对只有一个资金池，系统使用嵌套 mapping 存储映射关系，并通过地址排序（规范化）来消除输入顺序不同带来的歧义。这套精简而优雅的架构，是理解整个 Uniswap V2 协议的基石。
